## What works today

**First live round trip on 12 Oct 2026.** A real phone sent "Hello" to Meta's test number (+1 555 638 3300); the welcome menu came back, a button tap was received, and the order link was delivered and read. The same evening a real order (#1001, QAR 179) was placed from the phone and paid on the stand-in payment page, and both confirmations were delivered. A booking was made and confirmed the same way. **Templates (ALY-20):** notices inside a customer's 24-hour window go as ordinary messages in the module's own wording; after it closes they go as one of 16 templates in `core/templates.py`, each in English and Arabic. All 32 were submitted to Meta on 12 Oct. On 13 Oct, 31 were still pending and Meta had refused one (the Arabic booking reminder: too few words for three blanks); it was reworded and resubmitted the same day. Until Meta approves a template, sending it fails. `scripts/api-in-docker.sh uv run python -m alyr.templates_sync` shows where each stands, and `--create` submits any that are missing. A template sent outside the window has not yet been seen arriving on a phone. Six more, for the Catalog on WhatsApp (ALY-106), are in the catalogue and not submitted yet.

- Owner actions over WhatsApp: the workspace screen to link a number is in PR #79, not merged; a staff number is trusted only after it is linked, and the Arabic wording is a draft. Links at the end of an answer are off until the workspace has its own public address (`ALYR_WORKSPACE_URL`); the laptop tunnel does not serve it.
- **The pay page does not know an expired payment link.** Once a counted-stock pay-link order is unpaid after its hold, the link answers 409 and the page keeps showing the pay button. Fixed with the order page (ALY-112).
- **Orders cancelled before ALY-128 still have their sale on the customer's ledger.** From the fix on (branch `aly-128-credit-cancel`, migration 0025), cancelling an order put on a credit account writes a reversal beside its sale, tells the customer and leaves the order out of the aged-debt buckets, the weekly report and the Agent. Older cancelled orders were not repaired; on the demo shops that is a handful of rows, and the founder decides whether to reverse them.
- **"Coming" wording is out of the workspace, onboarding, order, booking, pay and tracking pages** (ALY-113 part 1; `test_no_unfinished_wording.py` fails if it returns). It is still on the public site (Payroll in the Products menu, "Early access" on the Chat page): the wording is the founder's to choose (the pull request lists every place). The pay page is still a labelled test page until a gateway exists.
- The public site's Arabic is unreviewed (ALY-66); the suite site (ALY-99) adds about three times as much Arabic, all of it a draft. Several product claims on it describe what is built on the simulator, not what runs live. See `docs/brand.md`.
- Bookings: one customer at a time per shop; services and opening hours can only be changed through the API; staff cannot move a booking or add a walk-in from the screen.
- On the founder's laptop Windows blocks Python's compiled database driver, so the API and its tests run through `scripts/api-in-docker.sh`.

- Templates carry no buttons, so a payment reminder sent outside the 24-hour window has the pay link but not the "pay now" and "I'll pay within a week" buttons. Templates exist on ALYR's test account only.
- Sign-in codes are not emailed yet: sign-in works on a local machine only.
- Self-serve sign-up is built and closed outside a local machine (`ALYR_SIGNUP_OPEN`): until the founder opens it, ALYR staff create a shop and its owner in the back office at `/ops`. What has to be true before opening it is the new section in `docs/runbooks/go-live-checklist.md`.
- Marketing consent cannot be captured yet (ALY-44), so every marketing template stays blocked. The one exception is `back_in_stock` (ALY-106), which rests on its own narrow consent, `back_in_stock`, given when a customer asks to be told about an item; that is not marketing consent.
- Arabic wording has not been reviewed by a native speaker.
- **A customer's order link and booking link are signed tokens** (`ALYR_LINK_SECRET`, 60 days, one purpose each; ALY-112 and ALY-133, the booking one in a pull request): no customer page takes a contact ID. - **For a demo, run `scripts/demo.sh up`.** It starts whatever is not running and ends with `check`, which says what to fix. `scripts/demo.sh reset` puts the demo shop back to its starting data (it asks first; it wipes chats).
- The API runs in Docker (`ALYR_DOCKER_FLAGS="-p 8000:8000 --name alyr-api-dev" scripts/api-in-docker.sh uv run uvicorn alyr.main:app --host 0.0.0.0 --port 8000`), the web app with `pnpm dev`, the tunnel with `cloudflared tunnel run alyr-dev`. All three must be running, on the founder's laptop.
- The tunnel publishes two addresses and nothing else: `api.alyr.online` (only `/webhooks/whatsapp` and `/health`) and `app.alyr.online` (only the customer pages `/s/`, `/b/`, `/pay/`, `/t/` and the API routes they call). The workspace, sign-in and the simulator answer 404 from outside.
- `ALYR_PUBLIC_WEB_URL=https://app.alyr.online` in `apps/api/.env` makes links in chats point there. It is the Next.js dev server behind the tunnel, which is acceptable for testing only (ALY-63 replaces it).

## Publishing the public site

**Where it stands on 29 Oct 2026** (this bullet is current; the older bullets below describe how publishing grew):
- **Accounts.** `alyr.qa` and `alyr.online` run in the business Cloudflare account (akmal@alyr.qa). The repository secrets `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` point there, so `site-deploy.yml` publishes on a push to `main`. The laptop fallback is `pnpm site:deploy` with the business login only.
- **What the production build carries:** the PostHog key (D-070, repo variable `POSTHOG_PROJECT_KEY`) and Bing's ownership tag `msvalidate.01` (repo variable `BING_SITE_VERIFICATION`). If the tag is dropped, Bing un-verifies the site.
- **Search tools (ALY-228):** Google Search Console has the domain property `sc-domain:alyr.qa`, verified through DNS; its sitemap was read with 18 pages. Bing Webmaster Tools is verified by the tag, with the sitemap submitted.
- **Crawlers (ALY-229):** Cloudflare allows search, agent and training crawlers, and Crawler Hints is on.
- **The app:** `deploy-gcp.yml` deploys it from GitHub through Workload Identity: `gh workflow run deploy-gcp.yml --ref main -f deploy=true`.
- **Watching:** Google Cloud uptime checks run every 5 minutes, on the Cloud Run addresses and on the public ones (`alyr.qa`, `app.alyr.qa/login`, `api.alyr.qa/health/ready`, where WhatsApp messages arrive). There is also an error alert. All of them email akmal@alyr.qa (`infra/gcp/setup.sh monitoring`).

- The public pages are published as plain files on Cloudflare (Worker `alyr-site`, static assets, free plan): `/` and `/chat` with their Arabic pages today; the suite site (ALY-99) adds `/bookings`, `/agent` and `/accounts` and their Arabic pages, which `scripts/build-site.sh` copies. The workspace, sign-in and the API are not there: `/whatsapp`, `/login` and `/api/...` answer 404 on `alyr.online`.
- To publish a change: `scripts/build-site.sh`, then `npx wrangler deploy` from `apps/web`. It needs the Cloudflare sign-in on the founder's laptop and the founder's go-ahead each time. Nothing deploys automatically. **In a pull request (site tooling, branch `aly-site-tooling`, not merged):**
  - **Publishing from GitHub:** a preview per pull request; production only after the founder approves in GitHub; `pnpm site:deploy` on the laptop as the fallback.
  - **A stamp:** `/version.txt` names the commit that is live.
  - **A CI site job:** the real build, EN/AR parity, banned words and prices, and links.
  - **Machine files:** `llms.txt` and a markdown copy of each page.

  Before the GitHub deploy can run, the founder adds two secrets, a `production` environment and version URLs (`docs/runbooks/site-deploy.md`, Needs Akmal). Rollback: the same runbook.
- Waiting for the next publish: the `/chat` accessibility fixes (ALY-97). With them, axe-core finds no issues on `/chat` and `/ar/chat` at 1440 and 390 px.
- The bare domain is attached as a route because it already had a proxied DNS record; `www.alyr.online` is a custom domain. See `apps/web/wrangler.jsonc`.
- **`alyr.qa` is the main address** since 12 Oct. `alyr.online` and both `www` forms redirect to it (`REDIRECT` is `"on"` in `apps/web/wrangler.jsonc`), and every plain `http` request is moved to `https`. If `alyr.qa` ever stops resolving, set `REDIRECT` to `"off"` and deploy: every address then serves the site itself. `api.alyr.online` is not affected.

## Things that only exist on the founder's laptop

A cloud session does not have these, by design:

- `apps/api/.env` and `apps/api/.env.neon` (secrets; never committed).
- The Cloudflare and Neon command-line sign-ins. Neon project `fragrant-firefly-99152608` (Frankfurt) holds demo data only.
- The Cloudflare Tunnel `alyr-dev` and its credentials: the live WhatsApp webhook is served from the laptop until always-on hosting is chosen (D-013). It only answers while the laptop, the API and the tunnel are all running. Live Meta testing therefore happens on the laptop, not in a cloud session.

## Working in a cloud session

- No Docker there. `scripts/cloud-setup.sh` starts the installed PostgreSQL, creates the same role and database as `docker-compose.yml`, installs dependencies, migrates and seeds. A session-start hook in `.claude/settings.json` runs it automatically in Claude Code cloud sessions.
- Then `scripts/check.sh` runs everything CI runs.
- This script was written on Windows and has not yet been run in a cloud session. If it fails, fix it in its own pull request.
