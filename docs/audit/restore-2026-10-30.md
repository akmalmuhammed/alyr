policy, the application role could connect, and the data was current to within seconds of the moment
chosen. The steps after the clone (rewriting the two secrets and restarting the API and worker) were

## What was done

1. `infra/gcp/restore.sh rehearse` read the newest recoverable moment
   (`gcloud sql instances get-latest-recovery-time alyr-db`) and cloned `alyr-db` to it:
   `alyr-db-rehearsal-20261029`, same region (`me-central1`), same private network, same tier
   (`db-g1-small`, the smallest tier ALYR runs; `gcloud sql instances clone` has no tier option). It landed in zone
   `me-central1-c`; production is in `-b`. It took a **different private address** from the
   production instance, in the same private range, which is the fact the runbook is built around.
2. A one-off Cloud Run job ran the API's image inside the private network, as the account the
   migration job uses, and counted rows. The database secrets are read by Cloud Run for that
   job, never by the script or by Claude; the job swaps the address inside its own process.
3. The clone was deleted, and `gcloud sql instances list` and `gcloud run jobs list` confirmed that only
   `alyr-db`, `alyr-db-export` and `alyr-migrate` were left.

It was done **twice**: the first run's script stopped waiting after gcloud's ten-minute limit and
left the clone behind (below); the clone was finished, checked and deleted by hand with the script's
own commands, then the corrected script was run end to end to prove it.

## What the rehearsal found

1. **A clone gets a new private address**, as the audit said. Both `database-url` and `migration-url` hold the
   address, so both must be rewritten and the API and worker restarted. `restore.sh repoint` does it.
2. **`gcloud sql instances clone` stops waiting after about ten minutes** and exits with an error while the
   clone carries on. The script now starts the clone and waits by itself. (This is what went wrong in run 1: the
   error also hit a cleanup bug of mine, a variable that was out of scope, so the clone was not deleted
   at once. It was found within minutes and deleted by hand; it lived about 6 minutes longer than planned,
   16 minutes in all, which costs cents.)
3. **A clone inherits deletion protection**, so it cannot be deleted until that is turned off. It also takes its
   own first backup (about 90 seconds) once usable and refuses a delete until that ends.
4. **A restored instance has a new name that cannot be reused for about a week**, so it never goes "back" to
   `alyr-db`. The things keyed to the name are listed in the runbook (the export job, the export
   bucket's permission for the new instance's account, the database alerts, `setup.sh`).
5. **The API's account can no longer read `migration-url`** (ALY-268 is live): the check job first failed with "Permission
   denied on secret". Any new job needing the owner credential must run as the account the migration job uses.
6. **Point-in-time recovery follows the clock closely.** The newest recoverable moment was between about 1.5
   and 5 minutes behind real time, and the clone held every write up to the moment asked for.

## Not covered

- Restoring a nightly **backup** (as opposed to a point in time) into a new instance, and importing the **export**
  file. The export-to-import path was rehearsed on 27 Oct with demo data (`infra/gcp/README.md`).
- Pointing the apps at a restored instance, and how long that takes (estimated, above).
- A restore with a realistic amount of data.
- Anything outside Google: Cloudflare, Meta, the R2 photos.
- A person doing it cold. The runbook was written to be followed by a tired person; nobody but its author has
  followed it yet.
